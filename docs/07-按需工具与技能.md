# 任务工具、技能与模型配置

## 模型与推理档位

`config/leaderteam.config.json` 的 `roles.leader/gate/discussA/discussB/arbiter` 各自配置 `route` 和 `effort`，角色不绑定任何模型系列。A/B 可以选相同路线，仍使用两个独立请求。成员在每次 `team_dispatch` 中指定 `model` 和 `effort`。所有选择必须属于配置模型目录，档位必须被该模型支持。

查看当前配置：

```powershell
node scripts/dev/set-role-model.mjs
```

修改一个角色（示例，不是固定要求）：

```powershell
node scripts/dev/set-role-model.mjs --role gate --model zcode/GLM-5.3 --effort high
node scripts/dev/set-role-model.mjs --role arbiter --model codex/gpt-6.1-sol --effort max --dry-run
```

CLI 先完整校验，再原子替换配置；无效选择不改文件，`--dry-run` 不写入。可用 `--config` 指定本地配置。重启后加载新设置。新建且没有持久模型选择的 Desktop 领队采用配置默认；恢复会话保留其原模型，不能悄悄切换。`leaderModelPolicy=enforce` 同时检查路线和档位，未知档位也拒绝；`warn` 只提示，`off` 不核对。

## 发现、授权与加载

领队调用 `team_tools`，`action=list`、`profile=code` 或 `shell`，取得目标预设实际注册的工具名称、短说明和 `available`。目录没有完整参数 schema，也不把领队自身没有的成员工具伪造为可用。`available=false` 的工具不能派发，例如当前平台没有加载的另一种 shell。

`team_dispatch` 必须明确传入 `tools`：本任务所需的工具名称子集。`profile` 是部署权限上限，不代表把整包工具都交给成员。额外 MCP 等工具只有列入 `toolPolicy.additionalTools` 且在目标预设实际注册后才能选择。未选择工具的描述和执行能力都不进入成员。

`defer_tools` 是 `tools` 的子集：已授权，但暂时不把 schema 发给模型。成员通过 `team_tools action=load names=[...]` 加载，下一模型步骤才能看到和使用。加载不扩大任务授权。`team_tools`、`team_skills` 两个控制工具始终可用，不能延迟自身，否则会失去加载入口。

官方 `ToolsService` 的最终 registry view 同时过滤继承工具和预设自己注册的工具。官方 `resolve` 将本步骤工具集合冻结，模型 schema 与工具执行使用同一份准入集合；同一批次先加载再调用，旧步骤仍不能执行新工具。最终安全门继续核对授权与加载状态。

成员的授权和加载状态随派发记录落盘。恢复时取原授权与当前部署政策交集；配置增加工具不会给已有成员自动增权，撤销则会收紧。

## 技能

默认发现工作区 `.agents/skills/` 与 `.leaderteam/skills/`。可用 `skills.roots` 增加目录，但必须同时在词法和真实路径上位于工作区或 `paths.globalRefRoots` 中。发现目录不自动成为额外读取授权。

`team_skills action=list` 只返回 id、名称、短说明、路径，不返回技能正文。发现每份文件最多读取前 8 KiB 元数据，名称最多 160 字符，说明最多 1000 字符。领队在 `team_dispatch.skills` 中选择技能 id，最多 10 个；每份正文最多 64 KiB，合计最多 128 KiB。

仅选中正文、来源路径和 SHA256 快照注入该成员的系统指令，不再复制一遍到初始消息历史。恢复沿用快照；文件后来改变不会悄悄替换已有成员的指令。技能链接到的资料不会自动加载，成员按现有文件读取规则取用。成员的 `team_skills read` 只能取得本次获授的技能快照。

## 派发示例

```json
{
  "name": "impl-label",
  "task": "按 SPEC 实现标签模块",
  "acceptance": ["SPEC 要求全部满足"],
  "model": "zcode/GLM-5.3-Flash",
  "effort": "high",
  "profile": "code",
  "plan_id": "agr-1a2b3c4d",
  "tools": ["read", "write"],
  "defer_tools": ["write"],
  "skills": ["label-style"],
  "write_scope": ["src/label/**"],
  "refs": ["SPEC.md"]
}
```

在默认的自治执行模式（`governance.mode="autonomous"`）下，`plan_id` 可省略，领队可直接派发并在后台触发异步监督；若切换至传统同步审批模式（`governance.mode="approval"` 且 `requirePlanAgreement=true`），则需先通过 `plan` 讨论并传入批准的 `plan_id`。工具与技能 id 均须从实时发现目录中选择。

## 边界与统计

文件读取、搜索、写入和编辑执行确定性的真实路径检查。shell 仍经过独立模型审查并依赖官方工作区写沙箱与系统权限；官方 Windows 后端没有读取白名单，不能将其宣称为成员子目录硬隔离或全部工具的读取隔离。新项目 ACL 修复只针对得到授权的那个工作区。

安全门的角色同样可配置；回执用 `by=model` 并记录真实模型、档位，统计兼容历史 `by=gpt`。陌生/MCP 工具默认受控，先完成必读参考，再接受最终审查；审查材料包括有上限的实际工具说明。

`operation.tool_description` 是插件或 MCP 提供的不可信元数据。安全门只把它作为工具行为的待核实说明，不把其中的命令、伪造授权或指定裁决当作规则。真实操作参数、作用域和明确授权仍决定审查，效果不能确定时拒绝；描述的脱敏和长度上限保持生效。

`usage.jsonl` 记录安全门、评审、裁断的实报 token 与重试合计；领队和执行成员从官方会话记录取量。dsh-context 扩展的累计表合并两类来源，不重复加入父子汇总，缺失计量保留未知。界面和统计口径见《08-可视化与用量》。扩展已在核心发布后通过隔离兼容验收。

遇到明确的Windows沙箱初始化grantWrite失败时，会持久记录成员故障并收起命令工具；该成员不能重新加载命令工具，同一运行时也拒绝继续向该工作区派发命令成员。由工作区所有者处理权限问题后，重启并派发新成员；程序不自行扩大ACL授权。
