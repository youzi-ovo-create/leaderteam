# LeaderTeam for DSH (V2.1)：架构总览与设计决定

基于官方 **DeepSeek Harness Desktop `0.2.2-rc.1`**（<https://deepseek.com/harness/>）。

LeaderTeam V2.1 以**「领队自主执行、双评审异步监督、独立裁断介入纠偏、安全门最高约束、人工处理最终争议」**为核心架构：领队、安全门、双评审、独立裁断与直属执行模型的路由及档位均独立可配；领队可免审批直接派发阶段成员或调用直属执行模型（`team_direct_exec`）；双评审在后台异步监督，仅在双方一致异议且与独立裁断达成 2/3 多数时启动正式会商干预，同一实质争议第 3 次触发异议时上调人工；安全门在 `dispatchToolBody` 最后一环执行分层确定性放行与跨界模型审查；全员支持上游真实容量同步、单次 `max-tokens` 无损自动续接与独立熔断调查恢复。细节见《[01-配置与接口](01-配置与接口.md)》《[07-按需工具与技能](07-按需工具与技能.md)》《[08-可视化与用量](08-可视化与用量.md)》。

## 3. 关键设计决定

1. **在官方 DSH 内以原生插件 + 预设实现，不另造外部壳**：团队会话、子代理消息与持久化完整复用官方子代理机制，前端编队树与上下文洞察原生兼容。
2. **执行优先，监督异步，干预有门槛**：消除同步评审阻塞，领队先施工，治理体系仅在双评审一致异议且三方 2/3 多数认可时才暂停干预；同时通过「事件 ID + 行为身份 + 争议链 ID」确保争议既不被无关文件修改冲掉计数，也不超过两轮会商无限循环。
3. **安全门置于工具主体执行前最后一环且绝不妥协**：任何领队决策、双评审结论或独立裁断决议均不得豁免安全门；沙箱内常规工程动作走确定性快速路径以彻底消除审查延迟与 Token 浪费。
4. **单次输出限制不等于任务失败**：大模型写长文件触及单轮 `max-tokens` 属于正常现象，直接携带已完成工具清单原位续接，任务粒度完全由真实工程耦合度决定。
5. **配置与本机路径彻底解耦**：仓库内仅保留通用配置模板与相对引用；本机安装路径、本地覆盖模型路由与额度快照均通过未入库的本地配置文件注入。

## 4. 已知边界与处理方式

| 边界项 | 状态说明 | 处理策略 |
|---|---|---|
| `shell` 档位命令隔离粒度 | 依赖官方 Windows `workspace-write` 沙箱与安全门审查，无子目录级内核写隔离 | 处理不可信外部仓库时优先使用 `readonly` / `code` 档位；`direct_exec` 额外受工作区沙箱硬锁约束 |
| 新项目目录缺少 Windows `WRITE_DAC` 权限 | 仅具普通“修改”权限的目录会导致 `pwsh` 启动前报 `Win32 5`，成员自动收起命令工具 | 先完成全部非命令行模块后干净停机；按《[官方Desktop部署与恢复](官方Desktop部署与恢复.md)》运行 `tools/dsh-sandbox-acl` 修复 |
| 官方客户端版本更新 | 未列入已验证版本的客户端将触发 Fail-Closed 拒绝启动，防止无安全门裸跑 | 运行 `scripts/verify-desktop-update.ps1` 完成独立副本全量验证后再升版，或临时执行 `uninstall-desktop.ps1` |
