# V2.3 原生模型映射与跨轮回读指南（Model Mapper & Cross-Round Readback）

本文介绍 `dsh-leaderteam` `2.3.0` 新增的原生模型映射器（Rust Node-API Mapper + 宿主桥接）功能、配置方法与运行边界。

---

## 1. 支持平台与宿主范围

- **支持并已通过真机验收的平台**：
  - `Linux x86_64`（`glibc >= 2.39`，如 Ubuntu 24.04 x86_64 及同级发行版 / WSL2 Ubuntu-24.04）
  - `Windows x64`（同时支持独立 Node.js 进程与官方桌面端 Electron 进程）
- **支持的宿主版本**：DeepSeek Harness **`0.2.2-rc.1`**（官方 Windows Desktop）与 **`0.2.2-rc.5`**（CLI / Web）。Node.js 要求 `>= 22.15`（推荐 `22.19+` 或 `24.x`）。
- **其他平台行为说明**：
  - `macOS`：包加载时自动跳过原生 Mapper（返回 `null`），不启用 V2.3 原生映射特性；
  - `Linux arm64`、`Windows arm64` 或基于 `musl` 的 Linux（如 Alpine）：由于发行包仅内置 `mapper.linux-x64.node` 与 `mapper.win32-x64.node`，加载时会明确报错提示缺少对应架构原生模块（Fail-Closed）。

安装后可通过诊断工具核验原生模块加载状态：

```bash
node bin/lt-doctor.mjs
```

当输出中 `NATIVE_MAPPER` 检查项为 `pass` 时，表示当前平台的原生映射器已正常就绪。

## 2. 核心能力：执行编号、异构备用链与跨轮回读

在多网关、多供应商异构编队中，首选模型可能因通道瞬时不可用（如 HTTP `404`、适配器缺失或服务临时故障）切换到备用路由，或由聚合网关转发至具体子型号。V2.3 原生映射器解决三件事：

1. **稳定执行者编号（`executor_n` 与 `round`）**：
   - 领队调用 `team_dispatch`（或 `team_direct_exec`）时，若省略 `executor_n`，系统自动分配递增的正整数执行号 `n`（从 `round = 1` 开始）；
   - 若后续派工显式传入已完成的 `executor_n`，系统沿用同一执行号并将轮次推进至 `round + 1`（同一 `executor_n` 在途运行或暂停会商期间不允许并发重入）。
2. **零工具副作用前提下的备用路由切换（`team.executionFallbacks`）**：
   - 当执行成员的首选路由因上游不可用失败时，系统严格核查当前回合的工具事件计数（涵盖工具调用、返回、流式工具块及安全门回执）；
   - **仅在未检测到任何工具调用尝试时**，自动按配置顺序尝试备用路由（每次切换仍完整执行配额、5 小时窗口与安全门准入检查，并按该候选自身的 `maxTokens` 上限发送请求）；一旦成员已发生过任何工具调用尝试或收到明确策略拒绝（`CONTENT_REFUSED`），立即停止自动切换备用模型。
3. **紧邻上一轮事实回读（`previous_model`）**：
   - 领队复用 `executor_n` 开启新一轮时，可通过 `previous_model` 填入其认知中该执行号紧邻上一轮实际完成任务的模型路由或型号 ID；
   - 原生核心将其与团队持久账本 `mapping.jsonl` 中紧邻上一轮已落盘的观测回执比对，返回 `match`、`mismatch`、`unverifiable`（上一轮失败无有效观测，绝不跨轮拿更早成功记录顶替）、`no_prior` 或 `omitted`；
   - **柔性记账原则**：回读结果仅作为事实回执写入账本并提示领队（工作区代码与测试客观证据始终优先于模型标签），不会将 `mismatch` 或 `unverifiable` 变成阻断正常施工的硬门禁。

## 3. 配置说明

### 3.1 执行成员备用路由链（`team.executionFallbacks`）
在 `leaderteam.config.json` 或 `leaderteam.local.json` 中，可为首选执行路由配置有序备用路由数组（所有路由均须存在于 `models` 与 `roles.executionPool` 中）：

```json
{
  "models": {
    "codex/gpt-6.2-sol": {
      "family": "gpt",
      "vendor": "openai",
      "efforts": ["medium", "high", "max"],
      "defaultEffort": "medium",
      "maxTokens": 65536,
      "uses": ["leader", "execute"]
    },
    "zcode/GLM-5.4": {
      "family": "glm",
      "vendor": "zhipu",
      "efforts": ["medium", "high", "max"],
      "defaultEffort": "high",
      "maxTokens": 16384,
      "uses": ["execute", "discuss"]
    }
  },
  "team": {
    "executionFallbacks": {
      "codex/gpt-6.2-sol": ["zcode/GLM-5.4"]
    }
  }
}
```

### 3.2 显式供应商标注（`models[route].vendor`）与四层记录边界
`mapping.jsonl` 严格区分以下四层记录，不混淆猜测：
- **配置目标（`target`）**：派发请求的目标路由；未收到有效回复时 `actual` 为 `null`；
- **宿主路由（`proof: "host_route"`）**：DSH 宿主实际调用的 `provider` 与 `model`；
- **上游披露型号（`proof: "upstream"`）**：当上游通过受支持的 `pi-ai` v2 回复信封披露具体 `responseModel` 且异于宿主请求型号时记录（反映网关披露值，不等同于对物理权重的独立审计）；
- **目录供应商（`vendor`）**：来自 `models[route].vendor` 的显式配置归因（不会仅凭路由名前缀自动推断厂商）。

### 3.3 跟随领队路由（`"default"`）
非领队角色（如 `gate`、`discussA`、`discussB`、`arbiter`、`directExec`）或成员派发目标可将 `route` 显式设为 `"default"`，表示跟随当前 `roles.leader` 的模型路由与推理档位（仍正常执行各角色自身的配额、窗口与安全准入校验）。若配置中整项省略可选角色 `roles.serialReviewer`，系统默认继承独立评审 `roles.discussA` 以保持独立审查语义。

## 4. 与开源版 `V2.2.x` 的安装切换说明

开源维护版（`dsh-leaderteam@2.2.1`）与闭源发行版（`dsh-leaderteam@2.3.0`）使用相同的插件包名 `dsh-leaderteam`，数据目录结构向前/向后兼容：

```bash
# 从 2.2.1 升级至 2.3.0（保留现有 leaderteam.local.json 配置与历史会话账本）
dsh plugin --profile web add ./dsh-leaderteam-2.3.0.tgz
# 或官方 Windows Desktop：
dsh plugin --profile desktop add ./dsh-leaderteam-2.3.0.tgz

# 如需回退至开源维护版 2.2.1（旧团队生成的 mapping.jsonl 会被 2.2.1 安全忽略，不影响核心运行）
dsh plugin --profile web add ./dsh-leaderteam-2.2.1.tgz
```
